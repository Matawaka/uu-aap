# Переносимое evidence действия / Сравнительный replay-пилот v0.1

**Статус: внутренняя воспроизводимость готова; внешние доказательства ожидаются.** Это экспериментальный интеграционный слой над существующим AI Gateway. UU Society остаётся на v1.2; Stable Core не изменяется.

Цель — подготовить один GitHub-сценарий к воспроизведению внешним инженером и будущему сравнению с его текущими инструментами. Пакет содержит scoped представления approval/permit, точную цель, результат старого планировщика, записи попыток и outcome. Все 17 случаев синтетические. Исторический live acceptance закреплён только как справочный источник.

## Что реализовано

1. Генератор использует неизменённый Node harness, сверяя четыре predecessor-файла по SHA-256.
2. Отдельный offline verifier принимает произвольный входной пакет заданной схемы, проверяет целостность, связи, scope, заявленные временные окна и chronology, роли frontier и противоречивые записи повторного использования.
3. Один и тот же evidence проверяется единым файлом и в виде восьми отдельных файлов. Оба профиля получают одинаковые условия и один checker.
4. Закрытые schemas, фиксированный протокол, первоначальные результаты, реальные отрицательные findings и исправления verifier сохранены. Отдельный CI повторяет suite и hostile/metamorphic проверки.

Выход verifier — проверка согласованности записи. Синтетические approval/permit не являются выданными Core receipts. Подлинность источника, реальные полномочия, live state, trusted time, атомарное потребление разрешения и факт внешнего действия не доказаны. Все соответствующие assurance-флаги остаются false. Код не вызывает GitHub и не исполняет merge.

## Запуск

Нужны Python 3.11+, Node 20+ для генерации и установленный `jsonschema==4.26.0`. Сетевая установка зависимости выполняется до offline replay.

```sh
PILOT_PATH=protocols/integration/ai-gateway/replay-pilot/v0.1
python3 -m pip install -r "$PILOT_PATH/requirements.txt"
PILOT_WORK=$(mktemp -d)
python3 -B "$PILOT_PATH/validate_package.py"
python3 -B "$PILOT_PATH/run_replay_pilot.py" suite --output "$PILOT_WORK/replay" --check-reference
python3 -B "$PILOT_PATH/verify_evidence.py" --pack "$PILOT_WORK/replay/P07/pack.json"
python3 -B -m unittest discover -s "$PILOT_PATH" -p 'test_*.py' -v
```

Для проверки вне репозитория достаточно `verify_evidence.py`, `evidence-pack.schema.json`, `source-bindings.json`, экспортированного `pack.json` и заранее установленной Python-зависимости. Node для проверки не нужен. Такая переносимость проверена нами локально, но не является независимым внешним acceptance. CLI не перезаписывает существующие экспорты. Exit 0 не создаёт ActionPermit.

## Фактические результаты

**P00–P16: 17/17 conform.** Один согласованный план; две согласованные observation-записи; шесть replay-denied; три indeterminate; два конфликта; три invalid evidence. Полная таблица каждого случая находится в [EN README](README.md#preregistered-cases-and-actual-results) и `reference-results.json`.

- Различий verdict между упаковками: **0**. Это локальное сравнение представления данных, а не исполнение AWS/Arcade или доказательство security superiority.
- Данных на случай: **1 файл против 8**, без общих файлов verifier/schema/dependencies.
- Сериализованные данные: **89 775 против 88 133 байт**. Единый файл больше на 1 642 байта; не заявляем экономию storage или времени расследования.
- P15: полностью переписанный, но внутренне согласованный пакет проходит consistency check; authentication остаётся false. Содержательный отрицательный результат сохранён.
- P10/P11: повторные записи обнаружены, но реальная конкурентная обработка не запускалась, атомарность single-use не доказана.
- P04/P05: сроки approval/permit проверяются новым verifier. Старый harness остаётся неизменным планировщиком своего контракта.
- P16: редактирование approval payload уменьшает проверяемость. Нехватка evidence не разрешает раскрыть защищённые данные.
- Vendor execution, внешний оператор, customer validation и willingness-to-pay: **NOT_EXECUTED / null**.

## Методология и исправления

Протокол записан до первого локального suite; это не независимый timestamped preregistration. Oracle ожиданий находится вне входа verifier. В первой hostile-проверке были 3 failures из 33 методов, во второй — ещё 2 из 35. Это дефекты новой реализации: неверный ID в error receipt, конфликт merge/non-merge, UNKNOWN с известным successor, несвязанный scope и newline в идентификаторе.

Прототипы, исходные failures и F01–F05 сохранены в `evidence/`. Исправлены реальные дефекты, исходные expected statuses не менялись. Первоначальный trace `b9c51595365f7538bd0250c68caf8aff32eb999ef4a196bd33e05a740041f5b8` сохранён. Исправленная проверка добавляет только один scope-mismatch reason в P09; все 17 статусов, входные пакеты и численные метрики прежние. Новый trace: `1f369a4bfda9e8fe37d2480f2d36b5abc1efa0d86030128b9a2079a8ac4143dc`.

## Реальный следующий gate

`comparison-plan.json` содержит заранее определённые метрики и правила парного сравнения, но vendor/version/config, participant, thresholds и измерения пока не выбраны. До реального прогона внешний участник должен зафиксировать baseline и критерии, затем отдельно сохранить свои команды, raw observations, hashes и ограничения. Измерять настройку, восстановление основания действия, ручные обращения к журналам, false allows/blocks, processing latency отдельно от ожидания человека и объём чувствительных данных.

Независимость нельзя установить только другим account label или самоописанием оператора. Готовность платить не выводится из нашего CI. Если преимущество не обнаружено, следует сохранить результат и сузить продуктовую гипотезу. Контакты с внешними участниками в этом слое не выполнялись.

## Инварианты

`Переносимость evidence != Подлинность полномочия`

`Согласованная запись != Фактическое действие`

`Обнаруженный повтор в журнале != Атомарное предотвращение`

`Меньше файлов != Быстрее расследование`

`Нет измерения != Нулевая стоимость`

`Неизвестный outcome != Разрешение повторить`

Связь с UU Society: v0.8/v0.9 исследуют структуру контроля и capture/recovery; v1.0 — качество evidence; v1.1 — ограниченный поиск; v1.2 — исходные evidence clocks и независимый renewal. Здесь эти принципы применены к подготовке проверяемого интеграционного опыта, без нового семантического Core-слоя. Институциональная независимость остаётся ограниченным и пересматриваемым утверждением, а не доступным системе абсолютным бинарным фактом.
